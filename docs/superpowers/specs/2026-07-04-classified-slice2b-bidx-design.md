## Problem

Stage 2 ships *verify this one record*: `verify(id, field, candidate)` answers over a single record's encrypted `_vdig` digest. Slice 2b adds *which records match*: an opt-in **equatable blind index** for `digest-only` fields (`password()`, `secretAnswer()`), materialized as a **store-visible** keyed tag per record (`_bidx`), plus `collection.findByDigest(field, candidate)` on top of it.

`_bidx` is the **only store-visible artifact in the entire classified design** and therefore the only frequency-leak surface visible **to a store without the DEK** (`_vdig` leaks nothing *to a key-less store*: encrypted, per-record per-write salts — Crypto #3 scoping. A DEK+backup holder can already unwrap `_cek`→CEK→vdig-key and dictionary `_vdig` per-record, so `_vdig` is not zero-leak against an *insider*). `_bidx`'s true delta over `_vdig` is therefore exactly three things: **(a)** a **key-less** store sees the equality partition (which `_vdig` never grants without the DEK); **(b)** the fixed per-(collection, field) salt amortizes the DEK-holder dictionary across all records at once (§5); **(c)** the tag survives `forget()` in a pre-forget backup (§2 forget). Everything below is shaped by making that leak (a) opt-in behind a double door, (b) exactly characterized, and (c) as expensive as possible to exploit.

## The candor constraint that shapes everything

Equatability **requires** a cross-record deterministic function of the value: equal plaintexts must produce equal tags, or there is nothing to index. Three consequences follow, none avoidable, all stated up front:

1. **The index key cannot be CEK-derived.** A per-record key cannot produce cross-record-equal tags. The key is collection-DEK-rooted (like `_det`, unlike `_vdig`) — which means `_bidx` has exactly the dekResidue exposure that I3 deleted for `_vdig`: a pre-`forget()` backup plus the collection DEK lets an insider test candidates against tags offline. We do not pretend otherwise; we price the attack (§1 slow-tag: ≥ 600K PBKDF2 per guess) and document it.
2. **Equal current values → equal tags, visible to the store.** The store learns the equality-partition of the collection on that field (not the values). Double opt-in door (§4) + mandated docs language (§5).
3. **Tags cannot be re-minted without plaintext.** `digest-only` never stores plaintext and `_vdig` digests are salted one-way commitments, so no rotation/backfill/migration path can ever regenerate a tag. Every "what happens on X" answer in §2 is downstream of this fact.

## 1. Keys and salt domains (all HKDF-SHA256, `deriveDeterministicKey` / `deriveVdigSlotKey` conventions)

| Key | Derivation | Usage |
|---|---|---|
| classify index key `K_idx` | HKDF(collection DEK, salt `'noydb-classify-index-v1'`, info `JSON.stringify(['noydb-classify-index-v1', collection, field])`) → HMAC-SHA256, 256-bit, **non-extractable, `['sign']`** | keys the `_bidx` tag; per-field (join-attack separation, §5) |
| classify index salt `salt_cf` | HKDF-deriveBits(collection DEK, salt `'noydb-classify-index-salt-v1'`, info `JSON.stringify(['noydb-classify-index-salt-v1', collection, field])`) → 32 raw bytes | the fixed per-(collection, field) PBKDF2 salt for the slow-tag inner digest |

Tag construction (**the slow-tag — a delta vs the stage-2 key table, see *Deltas***):

```
normalized = normalizeForVerify(policy.normalize, value)        // SAME code path as _vdig — no second pipeline
inner      = pbkdf2VerifyDigest(normalized, salt_cf, 600_000)   // fixed 32 bytes; existing enclave primitive
mac        = HMAC-SHA256(K_idx, inner)                          // fixed 32 bytes; a MAC, not ciphertext
tag        = base64(concat(COST_BYTE, mac))                     // 33 bytes: 1-byte cost/version discriminator ‖ 32-byte MAC
```

**Cost/version discriminator (Oracle #4 — resolved to the discriminator, not a freeze).** Unlike `_vdig`'s self-describing `{v, alg, iter}` payload, a raw tag carries no metadata and — the candor constraint — **cannot be re-minted** to a new cost. So a naive future 600K bump would silently turn every existing tag into a permanent miss. The tag is therefore prefixed with **one byte** `COST_BYTE` encoding `(version, iteration-tier)` (e.g. `0x01` = v1/600K). `computeBidxTarget` mints the target at the **stored tag's** discriminator when scanning legacy tags, and at the current default when minting new tags; a mismatched discriminator is a cheap non-match (no PBKDF2 at the wrong tier is attempted for that record — the target is only computed once per call, at step 2, so mixed-tier collections cost one extra target derivation per distinct tier present, bounded and rare). Rationale: forward-compat is one byte now and structurally impossible later; freezing 600K forever (the alternative) would foreclose the family's standard iteration-count ratchet. (The old "no `iv:` prefix" note is retired — the discriminator is that structural prefix.)

- **HMAC provides the keying** (M-2: without `K_idx` the store cannot test a single candidate — a bare or fixed-salt hash alone would be offline-dictionaryable by anyone with store access).
- **PBKDF2 provides the cost floor** (the I3 lesson applied to the index): a **DEK holder** *can* derive `K_idx` + `salt_cf`, so without the inner PBKDF2 an insider or backup+keyring holder could dictionary tags at HMAC speed — catastrophic for secret-class fields. With it, every offline guess costs 600K iterations. One guess tests **all records of the field at once** (inherent to equatability — stated, not hidden). PBKDF2-SHA256 is GPU/ASIC-friendly and the only cost floor `crypto.subtle` affords (Crypto #1, §4) — it raises the price, it does not make low-entropy fields safe; the **door** does.
- `salt_cf` is a **separate DEK derivation**, not `HMAC(K_idx, const)`. **This is a sign-key-hygiene choice, not a second security layer (Crypto #4).** Both `salt_cf` and `K_idx` descend from the *same* collection DEK, so the double-secret grants **no graded boundary** — a DEK holder re-derives both. The sole real rationale is that the `['sign']` HMAC key stays single-purpose (never also a source of raw bytes), and its non-extractability is defense-in-depth against a **leaked handle only** — a DEK holder re-derives raw `K_idx` via `deriveBits` regardless. A reader must not mistake the two secrets for two layers of protection. Both derivations rotate and die with the DEK together.
- Both derivations follow L-1 **from day one**: dedicated HKDF keys, never the raw DEK, no legacy form, therefore **no dual-query anywhere in this design**.

New enclave functions (ADDITIVE to the Contract v1 barrel): `deriveClassifyIndexKey(dek, collection, field)`, `deriveClassifyIndexSalt(dek, collection, field)`, `mintBidxTag(normalized, dek, collection, field)` (composes the three steps), `computeBidxTarget(candidate, policy, dek, collection, field)` (query side; normalize + same three steps). Implementation lives in `kernel/enclave/classify/bidx.ts` + `kernel/enclave/classify/find.ts`; `with-shape/classified/` keeps only the strategy member, delegating via the existing `active.ts` dynamic-import seam.

## 2. Envelope: the `_bidx` slot

```ts
// kernel/types.ts (EncryptedEnvelope) — new optional slot beside _vdig
readonly _bidx?: Record<string, string>   // field -> base64 33-byte tag (1-byte cost/version ‖ 32-byte keyed MAC), current value ONLY
```

**One tag per field per record — current value only.** The `_vdig` ring is **never** indexed: a tag-set covering ring entries would let `findByDigest` locate records by *past* passwords, a pure liability with no use case (conformance vector: after a rotate, `findByDigest(oldSecret)` returns `[]`).

**Integrity story — stated exactly, because it is the weakest slot in the envelope.** `_bidx` cannot be AAD-encrypted: the whole point is that its bytes are comparable without a key ceremony per record. It therefore has **no inline cryptographic integrity**. An adversarial store can (a) delete tags, (b) copy a tag from record A onto record B, (c) roll a tag back. The defenses, layer by layer:

- **Splice / forgery → neutralized for correctness by confirm-by-verify (§3):** `findByDigest` treats a tag match as a *candidate*, never an answer — every tag-hit is confirmed through the real `_vdig` verify path (AAD-bound, CEK-sealed) before its id is returned. A spliced or forged tag cannot produce a false id; it can only waste one PBKDF2. Claim for the audit: **`_bidx` is a zero-trust accelerator — no store manipulation of `_bidx` can cause `findByDigest` to return an id whose `_vdig` does not verify against the candidate.**
- **Deletion / rollback → misses only, detected forensically:** a deleted tag degrades `findByDigest` to a miss (availability, not integrity). `envelopePayloadHash` binds `_bidx` via the same **conditional widen** as `_vdig` (`envelope-body.ts` `envelopeBodyForHash`: bind only when present; no existing envelope carries `_bidx`, so no flag-day *provided the widen ships in the same slice as the first writer* — same law as stage 2). Ledger verification flags tag tampering/rollback after the fact. **Widen mechanics (SM #5, pinned):** the fast-path guard at `envelope-body.ts:105-123` (currently `_sealed===undefined && _vdig===undefined` → hash `_data` alone) MUST extend to `_bidx===undefined` so a vdig-only/bidx-absent envelope keeps its stage-2 byte-identical hash; and the `_bidx` segment MUST be appended **LAST**, after the `_vdig` segment, so a legacy vdig-only envelope hashes **byte-identically to its stage-2 value** (conformance vector, §6).

**Config-drift guard (C-A — a first-class enforcement point, not just store-tamper defense).** The `_bidx ⇒ _vdig` invariant below is a *writer* invariant; it holds only if every writer runs the classified codec. But a handle that opens `vault.collection('users')` **without** the `classifiedFields` option gets `cfg.vdigFields === null` (`collection.ts:741`); its codec skips the whole vdig/bidx block (`record-codec.ts:231`, gated on `vdigFields !== null`) and calls `encryptRecord` with `vdigCtx === undefined`. On a `put` that record's secret is either serialized into `_data` as **plaintext** (if the field is present) or the `_vdig`/`_bidx` slots are **silently dropped** (if absent) — and the existing fail-loud guard (`record-codec.ts:232`) never fires because it is itself gated on `vdigFields !== null`. Intra-session drift is already blocked by `collectionCache` (`vault.ts:862`); **cross-session/cross-process has no backstop today** — nothing persists that a collection has digest-only fields. This makes the partial-coverage contract dishonest (a tag can vanish, or the secret can leak, with no rotation, no `forget()`, no reviewed config change). Fix, symmetric to the `prev._sealed` R6 transition check at `record-codec.ts:249`:

- **Persist a marker.** On first classified write, record a collection-level `x-classified` marker (in the same persisted-schema record stage-2 already writes for digest-only fields — reuse it, don't add a store) that this collection **has digest-only/equatable fields declared**.
- **Fail loud on drift.** Any write whose codec has `vdigFields === null` but whose target `prev` **carries `_vdig` or `_bidx`** (or whose persisted marker is present) MUST throw **`ClassifiedConfigError`** (Refusal matrix **R10**) — never a silent plaintext write, never a silent tag drop. This is the enforcement point for `_bidx ⇒ _vdig` against **config drift**, distinct from the store-tamper defense (confirm-by-verify) below. It also hardens the *inherited* stage-2 `_vdig` drift (the same naive-handle hole exists for `_vdig` alone); whether to **back-port** this guard to stage-2 is an Open Question (see OQ list).

**Write path (C6 mirror — same codec block, same `{ id, prev }` context, extended per equatable field):**

1. **Field ABSENT → carry-forward (MONOTONIC, I-3):** copy `prev._bidx[field]` **verbatim** whenever `prev._vdig[field]` is being carried — **always, regardless of the writing handle's current `equatable` knob**. Coverage is monotonic: once a record carries a tag, an unrelated `put` never drops it. This is the fix for the flip-flop I-3 found — a lazy scrub that read the *writer's* knob let a handle with `equatable` removed silently retire a tag whose current secret was written while `equatable` was on, breaking `findByDigest` for every other handle. If the spec is equatable but `prev._bidx[field]` is missing (field predates the knob, or a future DEK rotation dropped it) there is **nothing to mint — no plaintext exists**; the record stays uncovered until its next secret rotate. **Tag retirement is never lazy** — it happens only through explicit `scrubEquatableTags(field)` (see *Transitions*) or `forget()`/clear/DEK-rotation.
2. **Field present with a string → rotate:** `mintVdigSlot` already computes `normalized` once inside the enclave; `mintBidxTag` consumes the **same normalized value** (never a re-normalization — one pipeline, conformance-pinned) and the new tag replaces the old.
3. **Field explicitly `null` → clear:** drop `_bidx[field]` together with `_vdig[field]`.
4. **Any other type → `ValidationError`** (shared branch, unchanged).

**Envelope invariant (new, conformance-gated):** `_bidx[field]` present ⇒ `_vdig[field]` present. The writer never emits an orphan tag; a read-side orphan (store tampering) is inert — confirm-by-verify makes it unreturnable. The config-drift guard above keeps this true across handles that lack the classified config.

**Rotation story:**

- **CEK rotation → nothing happens, by design.** `_bidx` is DEK-rooted, not CEK-bound. `rotateRecordCek` (`record-keys/sealing.ts`) must carry `_bidx` **verbatim** into its rebuilt envelope, exactly like `_det`/`_tier` (`...(live._bidx !== undefined ? { _bidx: live._bidx } : {})`) — omitting this line replays the #306 Slice-A data-loss bug on the index. Conformance vectors: `put → rotateRecordCek → findByDigest hit` and `revokeSealedRecord({hard:true}) → findByDigest hit`.
- **DEK rotation → tags are dropped, and can never be healed lazily.** There is no `_det`-style L-1 dual-query self-heal: L-1's dual-query worked because both derivations came from the *same live DEK*; after a DEK rotation the old `K_idx` is unrecoverable and — the candor constraint — the tag cannot be re-minted from stored data (no plaintext, `_vdig` is one-way). Honest present-tense status: the only live DEK-rotation path (`with-party/team/keyring.ts` `rotateKeys`, `keyring.ts:806-822`) decrypts `_data` directly under the old DEK (`decrypt(_iv, _data, oldDek)`) and rebuilds bare `_iv/_data` envelopes — it hits an AES-GCM auth failure and **throws** the moment it reaches a `_cek` body, and digest-only requires `perRecordKeys` (R1), so **DEK rotation is unreachable today for every collection that can carry `_bidx`** (pre-existing limitation, not introduced here). **Caveat (D-5, verified-accurate):** "unreachable" means it **throws mid-operation, not that it cleanly refuses**. On a *mixed* collection (some bare `_iv/_data` records, some `_cek` records) `rotateKeys` re-encrypts the bare records first, throws on the first `_cek`, and never reaches the keyring update that persists the new DEK (it runs only after the loop) → the already-rewritten bare records are now encrypted under a DEK that was never saved and become **unreadable**. This is a **pre-existing `rotateKeys` hazard, not bidx-specific**; it is flagged here because `_bidx` carriers are exactly the `_cek` records that trip it. The only bidx-specific enforcement point is the forward requirement below. Forward requirement, binding on whoever builds perRecordKeys-aware DEK rotation: that path MUST **drop `_bidx`** (stale tags under a dead key are unreturnable garbage that still leaks the *old* equality partition) and MUST document that index coverage regrows only as secrets are individually rotated by writes.

**forget():** the tombstone slot-drop list extends to `_bidx` — a forgotten record's tag MUST NOT outlive the record (conformance vector: post-forget envelope has no `_bidx`; `findByDigest` misses). `buildTombstone`/`tombstoneHistory` already drop all body slots incl. `_bidx` for free (verified). Residue stated plainly (I3 discipline): unlike `_vdig` (CEK-only ⇒ shreddable by construction), `_bidx` is DEK-rooted — a **pre-forget backup** retains the tag and the DEK survives per-record forget, so a DEK holder can test candidates against the residual tag at 600K PBKDF2 per guess (the slow-tag floor). This is the **bidx-dekResidue class**.

**`classifySealedShred` shape change (SM #4 — a THIRD category, not additive).** The current two-bucket return `{ shreddable, dekResidue }` (`record-codec.ts:407-433`) cannot express `_bidx`, which is BOTH live-store-shreddable (tombstone drops it) AND dekResidue-in-backups. Reporting `_bidx` as either single bucket is a lie. The fix is a **shape change**: either a third array or a per-slot `{ field, class }` shape where a `_bidx` slot reports `class: 'live-shreddable + dekResidue-in-backups'`. This is a golden/shape change (not an additive field), flagged for the plan. It is the price of equatability, disclosed by the candor door — not a bug to fix by construction, because no construction can fix it (§ candor constraint, point 1).

**History & pods (M3 analog) — the residue is the FULL partition timeline, not one tag (I-4).** `_bidx` rides the envelope, so `_history` snapshots retain **every superseded tag**. A backup taken before prune (`dump()` embeds the whole `_history` collection, `backup.ts:108-112`; `.noydb` pods wrap `dump()`, `bundle.ts`) therefore preserves the record's **entire secret-change timeline** — every historical `_bidx` value, and which historical values *collided across records* — not merely a single current tag. §5 prices only a single current tag; the backup/pod residue is strictly larger. Prune clears only the **live** store; it does **not** reach a backup or pod already emitted, so **no post-hoc op retires a tag once it is in an emitted backup** (the I3 "disclosed, not fixable" framing — prune is the remedy *before* a backup, not after). `_history` is not synced (`loadAll` filters underscore collections), so historical tags travel **only** via backup — which is exactly why this matters. `.noydb` pods carry tags; they are keyed MACs, so the zero-knowledge posture vs a key-less holder is unchanged.

## 3. `findByDigest` — semantics, timing, consent

```ts
// kernel-api golden addition, gated behind withClassified()
collection.findByDigest(field: string, candidate: string): Promise<readonly string[]>
```

**Returns record ids, not records** (recommended over the `findByDet` return-records shape): the op is verdict-adjacent — minimal egress. Returning decrypted records would bundle a `'get'`-equivalent disclosure under a find op; callers `get(id)` afterwards under normal consent. Order: store enumeration order, unspecified (matches `queryByDet`).

**Algorithm (hub-side, single code path):**

1. Caller-bug refusals, thrown at ~0 elapsed, pad-exempt (R6 convention): field not declared classified / not `digest-only` / not `equatable` → `ClassifiedVerifyError`; candidate not a string → `ClassifiedVerifyError`; classified not enabled → `ClassifiedNotEnabledError` (strategy gains a `findByDigest` member; `NO_CLASSIFIED` gains the throwing stub).
2. `target = computeBidxTarget(candidate, …)` — **this step structurally costs one full 600K PBKDF2** (the slow-tag inner digest), and it runs **unconditionally BEFORE the scan** (I-1, pinned as a conformance vector). Not a dummy pad: real, unavoidable work on every call, including an empty collection.
3. Scan: `adapter.list` + one `adapter.get` per id; string-compare `env._bidx?.[field] === target` (the `findByDet` shape — **no envelope body is decrypted during the scan**), retaining each hit's **already-fetched envelope**. **No early return may precede step 2** — in particular an empty-collection `if (ids.length===0) return []` hoisted above the PBKDF2 is FORBIDDEN (that is the F1 inverted-economics leak: an empty collection would reply ~0 ms while a populated one pays 600K, letting a timing adversary learn "collection empty vs not" — a fact `[]`-either-way is meant to hide).
4. **Emit the single consent op now — after the scan, before confirm (Oracle #5):** `onAccess('find', '*')`, exactly once. Emitting it here (not after confirm) fixes its store-write timestamp to a post-scan time independent of hit count; emitting it after the confirm loop would leak sweep duration ≈ hit count as a temporal Δt (a leak independent of C-B).
5. **Confirm-by-verify — on the ALREADY-FETCHED scan envelope, never a second `adapter.get` (C-B).** For each tag-hit, decrypt `_vdig[field]` **from the envelope already in hand from step 3** and run the stage-2 verify **inner** (`verifyDigestField` INNER: decrypt `_vdig[field]` under its AAD, PBKDF2 the candidate at the payload's own salt/iter, blinded compare) **directly on that in-hand envelope**. It MUST NOT call the stage-2 `strategy.verify` wrapper, because that wrapper re-fetches via `ctx.getEnvelope(id)` (`verify.ts:62`) AND emits an `onAccess('verify', id)` op (`active.ts:49`) with the real id. Re-fetching would reintroduce the exact per-query pushdown leak §3 defers (a hit-only second `get` burst lets a remote store correlate each re-fetched id → its visible `_bidx` tag → which equivalence class was probed, when, and its size) and would also open a **TOCTOU** window (tag read at scan-time vs `_vdig` read fresh — a concurrent rotate between scan and confirm would silently drop a record that matched at scan). Reading the tag and `_vdig` from **one snapshot** removes both. Collect the id iff `ok: true`, discarding `mustRotate`. Tag-hits that fail confirmation are dropped silently — no error, no distinct observable (a splice is indistinguishable from a stale tag to the caller, deliberately). Confirm emits **no** per-hit consent op. Return the confirmed ids.

**Store-shape (C-B — now literally true):** `findByDigest` issues to the store exactly **`list` + N `get`** — one `get` per record during the scan, and **zero additional gets regardless of hit count**. It is therefore **indistinguishable in shape from `findByDet`** (which the pre-audit design's second-`get` burst falsified). This is a hard conformance vector (§6): a spy store records exactly `list` + N `get` for any candidate against any collection contents.

**Timing properties (F1/F2 lessons applied):** the caller legitimately receives the result, so result-correlated timing is not an oracle *to the caller*. The properties that matter and hold:

- **Guessing-cost floor:** every call costs ≥ 1 full PBKDF2 (step 2) regardless of store state — `findByDigest(candidate)` is never cheaper than `verify(id, candidate)` for any store contents, **including an empty collection** (falsifiable; conformance-vector this claim — an empty-collection call runs exactly one PBKDF2, wall-time-equal to a zero-hit populated call). Without the slow-tag, `findByDigest` would be an HMAC-speed whole-collection guessing oracle — strictly *worse* per guess than the C4-padded `verify`, an inverted-economics variant of F1.
- **No absence discount:** zero-hit and hit calls share steps 1–3 identically; hits add confirm PBKDF2s. Wall-time therefore correlates with the **tag-hit count** (Crypto #5 precision: this is confirmed hits **plus** any store-spliced false hits — the store knows what it spliced, so this is not an oracle to the store; and it is result-equivalent to the caller) — accepted and documented. No pad-to-max (unbounded) is attempted.
- The scan itself is O(N) adapter reads — visible to the store as a full sweep, indistinguishable in shape from `findByDet`/backup scans. The store never learns the target tag (compares happen hub-side).

**Consent op:** a **new `'find'` literal** joins the `onAccess` union (`'get' | 'put' | 'delete' | 'reveal' | 'verify' | 'find'` — additive union extension, kernel-api golden, same mechanism as stage-1 `'reveal'`). Recommended over reusing `'verify'`: a whole-collection sweep is a materially different disclosure than a one-record verdict, and the audit trail must be able to say so. **One entry per call** (Q6 precedent — per-match entries would leak match cardinality into audit-trail structure), emitted as `onAccess('find', '*')`. **`'*'` is a NEW consent-recordId sentinel introduced here (I-2 correction):** the earlier "verifyGroup convention" citation was **false** — `matchGroup` uses `'*'` only as an *error* record-id, never in a consent op, so `findByDigest` is the first op to write `'*'` as a consent recordId. Consent-audit consumers must treat `'*'` as **"no single record"** (a sweep marker), and a golden asserts `'*'` **cannot collide with a real store id** (ULIDs/user ids never equal `'*'`). The entry is emitted **BEFORE the confirm loop** (Oracle #5): its store-write timestamp is then a fixed post-scan time, not monotone in hit count (emitting it after confirm would leak sweep duration ≈ hit count as a temporal Δt independent of C-B).

**Union-widening sites (I-2 checklist — every one must widen together, or a downstream exhaustive switch breaks at its next in-range minor):** `ConsentOp` (`consent.ts:77`) is public and re-exported (`index.ts:454`) — klum-db and ui have exhaustive switches over it; the `onAccess` union on `collection-config.ts:307`; and the classified ctx `onAccess` type (`strategy.ts:30`). All three widen to include `'find'` in this slice; the plan enumerates them as a checklist so none is missed.

**Not a query-DSL operator — and why, stated for the audit.** The query DSL runs inside the hub *after decryption*, over plaintext views; digest-only fields have no plaintext view by construction, and stage 1/2 refuse them from every index and query surface (R3/R4). Admitting `where(field).equals(x)` sugar over `findByDigest` would erase the visibility of an audited, consent-bearing, PBKDF2-priced sweep inside ordinary query composition. `findByDigest` stays a dedicated, loud, top-level method (the `findByDet` precedent).

**The store-pushdown tension, flagged honestly.** A collection-scoped tag is, in principle, store-indexable: a `to-postgres` could index the `_bidx` column and answer equality in O(log n) without the hub scanning. This design **does not do that**, and the "stores never run queries" invariant survives *literally* (the hub scans `_bidx` exactly as it scans `_det`). But the audit should note: the invariant's survival here is partly definitional. A future pushdown (`NoydbStore.findByTag?`, optional capability) would (i) change the adapter contract — `@noy-db/hub/adapter` seam governance, forced rebuild across `noy-db-to`; (ii) hand the store a **new leak class**: per-query observation of *which* equivalence class is probed, how often, and when (login-attempt correlation) — strictly more than the at-rest frequency leak this spec prices. Deferred to a dedicated slice with its own audit; listed in Non-goals. The tag construction is deliberately pushdown-compatible so that deferral costs nothing.

## 4. Surface: presets + knobs (D2 law — declarative knob, no new preset)

```ts
classified.password({ minLength: 12, rotateDays: 90, notLastN: 5, equatable: true })
classified.secretAnswer({ equatable: true })

vault.collection<User>('users', {
  perRecordKeys: true,                 // R1, unchanged
  acknowledgeEquatableRisk: true,      // NEW collection-level candor door (det precedent)
  classifiedFields: { pin: classified.password({ equatable: true }) },
})
```

- `ClassifiedFieldSpec` gains `readonly equatable?: true`; `VdigFieldPolicy` gains `readonly equatable: boolean`. Default **absent/false — refused by default** (issue requirement).
- **Double door**, mirroring `deterministicFields` × `acknowledgeDeterministicRisk` exactly: the field-level knob declares intent; the collection-level `acknowledgeEquatableRisk: true` acknowledges the leak in the code the owner reviews. Either alone refuses (R8). **`acknowledgeEquatableRisk: true` on a collection with zero equatable members is a silent no-op** (R8 is one-directional, the `acknowledgeDeterministicRisk` precedent — acceptable, stated for candor: Oracle #8). Coverage is resolved by `_applyClassifiedFields` **first-wins**, so it is deterministic **per process, not per handle** (a second handle's differing config does not re-open it — the reconcile is first-wins).
- `describe()` / `toJSONSchema()`: `x-classified` emission gains `equatable: true` (additive metadata; UI/exporters may badge it). **Boundary note (Oracle #6):** `describe()` needs no `withClassified()` (`collection.ts:1045`) and `toJSONSchema()` emits `x-classified` **ungated** (`json-schema.ts:44`), so `equatable: true` is advertised to **any handle-holder and any shared/exported schema — beyond the DEK-consent boundary**. This is **intended**: equatability is a structural property a schema consumer (UI badge, exporter) legitimately needs, and it discloses only *that the field is equatable*, never a value or a partition. If a deployment does not want that advertised, gate `x-classified.equatable` emission behind the same door as the value-bearing metadata — flagged as a deployment choice, default-emit.
- Mandated docs language on both preset knobs (Crypto #1 + M-2 candor): *"equal values produce equal store-visible tags: anyone with store access learns which records share this secret and how many share each value — never the value itself. A collection-DEK holder can additionally test candidate values offline: the tag's inner digest is PBKDF2-SHA256 (600K), which is GPU/ASIC-friendly — an offline attacker runs on the order of 10⁴–10⁸ guesses/second, so for low-entropy secrets (PINs, casefolded secret answers) offline recovery of the equality partition is seconds-to-hours, not years. `crypto.subtle` exposes no memory-hard KDF (no scrypt/argon2) and the family's no-crypto-deps law forbids adding one, so PBKDF2-SHA256 is the hardest primitive available; the iteration count raises the price but does not make a low-entropy field safe. The real control for low-entropy fields is the DOOR — do not enable `equatable` for them unless the partition being learnable is acceptable — not the iteration count. Pre-forget backups retain tags."*

**Transitions (design position: the equatable knob is NOT a storage-form transition — no R6-style refusal):** the field's form stays `digest-only` throughout; toggling the knob changes only index coverage, with no data loss possible in either direction, so write-path self-heal replaces refusal. **Coverage is monotonic (I-3):** it only ever grows on a secret-rotate write and is never lazily retired; retirement is explicit-only.

- **Adding `equatable` to existing data:** old records carry `_vdig` but no `_bidx` and **cannot be backfilled** (no plaintext — the candor constraint). Allowed; coverage grows as each record's secret is next rotated. `findByDigest`'s documented contract is therefore: *"returns records whose **current** secret was written while equatable was on"* — mathematically the only implementable contract, stated rather than hidden (partial-coverage honesty).
- **Removing `equatable`:** allowed, but **tags are NOT scrubbed lazily (I-3 — the flip-flop fix).** The carry-forward branch (§2 branch 1) always copies `prev._bidx[field]` verbatim whenever `_vdig[field]` is carried, **regardless of the writing handle's current knob** — so a handle that has `equatable` removed can no longer silently retire a tag whose current secret was written while `equatable` was on (which would break `findByDigest` for other handles and make tag existence depend on whoever last touched the record). Retirement of the equality partition after removing the knob is **explicit-only**, via the maintenance sweep `collection.scrubEquatableTags(field)` (an envelope-rewrite, no crypto). This is the **sole drop-path** for a still-live record's tag (besides clear/`forget()`/DEK-rotation). Residual until the owner runs the sweep: tags persist on all records — documented, and the sweep is the remedy.

## 5. Threat model (2b deltas; stage-2 §5 carries in unchanged)

- **What an adversary with store access learns (the frequency leak, exactly):** per equatable field — the partition of records into current-value equality classes; each class's cardinality; class-membership churn over time (tag changes on writes; tag history in `_history` until prune). **Not** the values, and **not** the ability to test a candidate (tags are keyed; M-2). Cross-record equality is the *product*, disclosed by the door — e.g. "these 40 users share one password" is visible as structure.
- **Join attacks — why info-binding is load-bearing:** `K_idx`/`salt_cf` bind `[domain, collection, field]` via the injective JSON-array info (the `deriveSealedFieldKey` collision argument). Same value in two fields or two collections → unrelated tags; cross-vault → different DEKs entirely. A binding mistake (shared key across fields) would let the store join partitions across fields/collections — conformance vectors pin per-field and per-collection tag separation explicitly.
- **DEK-holder offline dictionary (bidx-dekResidue):** an insider with the collection DEK derives `K_idx` + `salt_cf` and tests candidates at the PBKDF2 floor per guess; one guess covers all records of the field (equatability amortization — stated). **Precise incremental exposure over `_vdig` (Crypto #2):** because `salt_cf` is a *fixed* per-(collection, field) salt, the DEK-holder dictionary cost is **O(dictionary) — invariant to record count N, history depth H, and backup count B**. Contrast `_vdig`'s per-record per-write random salts, which force a DEK holder to pay ~N·H·B·D×600K to dictionary the *same* population. That amortization is exactly what equatability buys the attacker and is the second of `_bidx`'s three deltas over `_vdig` (§Problem). Pre-forget backups retain tags (§2 forget). This is the class I3 eliminated for `_vdig` and equatability *necessarily* reintroduces for `_bidx` — priced, doored, documented; never claimed absent. See §4 for the honest cost band (GPU/ASIC, not per-core).
- **Backup/pod residue is the FULL partition timeline (I-4):** §2 above prices a single *current* tag; a **pre-prune backup or `.noydb` pod** embeds the whole `_history` collection and therefore every *historical* `_bidx` value — the record's entire secret-change timeline plus which historical values collided across records. No post-hoc op retires a tag once it is in an emitted backup; prune is the remedy *before* export, not after (disclosed, not fixable).
- **Online guessing:** `findByDigest` is a whole-collection oracle per guess — strictly stronger than `verify` per call, floored at the same ≥1-PBKDF2 cost, and separately audit-visible (`'find'` op). Low-entropy enumeration math goes in the preset docs verbatim (blood group: 8 calls partition the collection). Hub-side rate limiting stays out (stage-2 Q5 position); app-side hooks + consent audit are the controls.
- **Store tag manipulation:** splice/forgery → cannot produce false ids (confirm-by-verify, §2/§3); deletion/rollback → misses, forensically detectable via the ledger's conditional `_bidx` binding. `findByDigest` is thus **complete only over an honest store, sound over any store** — the asymmetry stated for the audit.
- **Returned-id ordering (Oracle #7):** `findByDigest` returns store keys; if a collection uses default ULID ids, the returned ids leak the matching records' **creation-time ordering** to the caller (ULIDs are time-ordered). Minor, caller-visible only; noted so a deployment that treats match-order as sensitive uses opaque ids.
- **Timing:** wall-time reveals **tag-hit count** — confirmed hits plus any store-spliced false hits (Crypto #5); result-equivalent to the caller and known-to-the-store for what it spliced, so not an oracle to either; accepted. No path is cheaper when records/tags are absent than the structural PBKDF2 floor (no F1-style inversion: the expensive step precedes the scan unconditionally, empty collection included — I-1).

## 6. Enforcement & governance

- **`enclave-body-only` ratchet extension (identifier-based, stage-2 M1 form):** outside `kernel/enclave/**`, no references to `deriveClassifyIndexKey`, `deriveClassifyIndexSalt`, `mintBidxTag`, `computeBidxTarget`, or the literals `'noydb-classify-index-v1'` / `'noydb-classify-index-salt-v1'` (conformance-kit files allowlisted). **Explicitly PERMITTED: opaque `_bidx` tag-map transit** — codec carry-forward, `sealing.ts` verbatim carry, backup/history plumbing. Boundary law unchanged: plaintext/digest/key ops = enclave-only; ciphertext-and-tag-map plumbing = anywhere.
- **Conformance vectors (each threat/branch above is represented; audit-added vectors flagged by finding):** round-trip put→findByDigest hit / wrong-candidate miss · per-field and per-collection tag separation (join-attack pins) · normalization-equivalence (secret-answer casefold variants → one tag; same pipeline as verify) · carry-forward byte-stability (unrelated put: tag bytes + ledger hash unchanged) · clear drops both slots · invariant `_bidx ⇒ _vdig` · `rotateRecordCek` + `revokeSealedRecord({hard:true})` preserve hits · **splice vector: tag copied A→B returns only A** · forget → no `_bidx`, findByDigest misses · ring-not-indexed: post-rotate `findByDigest(oldSecret) → []` · R7/R8 at both doors + R9 runtime (R9 one indistinguishable message across sub-cases — Oracle #6). Audit-added:
  - **C-B store-shape:** a spy store records **exactly `list` + N `get`** for `findByDigest`, **zero additional gets regardless of hit count** — byte-for-byte the same call sequence as `findByDet`; confirm reads `_vdig` from the in-hand scan envelope.
  - **C-B TOCTOU:** a rotate interleaved between scan and confirm does not silently drop a scan-time match (tag + `_vdig` come from one snapshot).
  - **I-1 empty-collection cost:** `findByDigest` on an empty collection runs **exactly one PBKDF2**, statistical wall-time-equal to a zero-hit populated call; no pre-target-compute early return exists (step-2-before-scan pinned).
  - **I-3 monotonic carry:** Handle A (equatable) mints r1's tag; Handle B (equatable removed) does an unrelated `put` on r1; Handle A's `findByDigest(r1-secret)` **still hits** (tag carried verbatim, not scrubbed) · `scrubEquatableTags(field)` is the only lazy-write-independent drop path (post-sweep: tag gone, `findByDigest` misses).
  - **C-A config-drift (R10):** a naive handle (`vdigFields===null`) writing over a record that carries `_vdig`/`_bidx` throws `ClassifiedConfigError` — never a plaintext `_data` write, never a silent tag drop.
  - **SM #5 ledger segment order:** a vdig-only / `_bidx`-absent envelope hashes **byte-identically to its stage-2 value** (fast-path guard extended to `_bidx===undefined`; `_bidx` segment appended LAST after `_vdig`).
  - **Oracle #4 version discriminator:** a tag minted at `COST_BYTE` v1 round-trips; a tag with an unknown/mismatched discriminator is a cheap non-match (no wrong-tier PBKDF2), and `findByDigest` still returns exactly one target derivation per distinct tier present.
  - **Oracle #5 consent ordering:** the single `onAccess('find', '*')` op is written **before** the confirm loop — its store-write timestamp Δt is independent of hit count.
  - **SM #4 shred shape:** `classifySealedShred` reports a `_bidx` slot in the new third/​per-slot shape (`live-shreddable + dekResidue-in-backups`), not as either single legacy bucket (golden/shape change).
- **Goldens (additive except where flagged):** enclave barrel +4 exports · kernel-api +`findByDigest` +`scrubEquatableTags` on Collection +`'find'` in the `onAccess` / `ConsentOp` union (three widening sites — I-2 checklist) · **`'*'`-non-collision golden**: the sweep-marker recordId `'*'` can never equal a real store id (ULID/user-id) · **`classifySealedShred` return-shape golden CHANGES** (SM #4 — third category / per-slot `{field,class}`; not additive) · root barrel unchanged (errors reused) · bundle gate — find engine rides the existing `active.ts` dynamic-import seam (stage-1 negative-test methodology).
- **Security review gate:** this design → adversarial audit (**done — this revision folds its 2 Critical + 4 Important + Minor/Info findings; Audit-resolution map above**) → plan → implementation (the M-2..M-5 rhythm). Post-hardening re-review focus: the C-A config-drift guard completeness, C-B store-shape parity (`list` + N `get`, in-hand confirm), I-3 monotonic-coverage soundness, the honest (GPU/ASIC) cost band, and the tag version-byte scan logic.
